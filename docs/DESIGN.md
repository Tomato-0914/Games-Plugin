# Chess-Plugin 设计报告（第一期：中国象棋）

> 适用框架：TRSS-Yunzai  
> 适用适配器：LLOneBot（OneBot v11）、QQBot-Plugin（QQ 官方机器人）  
> 状态：已确认，第一期已实现（见第 13 节确认结果）

---

## 1. 目标与范围

| 项目 | 第一期（本次） | 后续 |
| --- | --- | --- |
| 棋种 | 中国象棋 | 五子棋、国际象棋、围棋等，复用同一套房间 / 渲染 / 战绩框架 |
| 对战模式 | 群内双人对战；人机对战（群聊、私聊均可） | 观战、残局挑战、复盘 |
| 适配器 | LLOneBot、QQBot 官方机器人 | — |
| 插件维护 | `#棋类更新`、`#棋类强制更新`，参考柴郡插件 | — |

人机对战可以做，结论见第 6 节：用纯 JavaScript 写一个 Alpha-Beta 搜索引擎，放在 `worker_threads` 里跑，不阻塞 Bot 主线程，也不需要额外安装程序；另外留一个可选接口，可以接 Pikafish 这类外部 UCI 引擎，用来提供更强的难度。

## 3. 指令设计

前缀 `#` 可省略（与柴郡一致）。

### 3.1 对局指令

| 指令 | 说明 | 谁可用 |
| --- | --- | --- |
| `#象棋` / `#象棋帮助` | 玩法与指令说明 | 所有人 |
| `#发起象棋` / `#发起象棋 红` / `#发起象棋 黑` | 创建对局，等待对手；不指定颜色时加入后随机 | 群聊 |
| `#加入象棋` | 加入等待中的对局，加入后立即开局，红方先走 | 群聊，非发起人 |
| `#人机象棋` / `#人机象棋 困难 黑` | 和 Bot 下；难度：入门 / 简单 / 普通 / 困难，默认普通；颜色默认红 | 群聊、私聊 |
| 走子：`炮二平五`、`马8进7`、`前车进一`、`h2e2` | 当前行棋方直接发送，无需 `#` | 对局中轮到的人 |
| `#棋盘` | 重新发送当前棋盘 | 所有人 |
| `#悔棋` | 双人：需对方 `#同意悔棋`；人机：每局限 3 次，退回到自己上一步 | 对局双方 |
| `#求和` → `#同意求和` / `#拒绝求和` | 提和；人机模式下 AI 按局面评分决定是否接受 | 对局双方 |
| `#认输` | 立即判负 | 对局双方 |
| `#结束象棋` | 强制结束，不计战绩 | 发起人（未开局时）、群管理、主人 |
| `#象棋战绩` / `#象棋战绩 @某人` | 胜 / 负 / 和、胜率、积分 | 所有人 |
| `#象棋排行` | 本群积分前 10 | 群聊 |

### 3.2 插件维护指令

| 指令 | 说明 |
| --- | --- |
| `#棋类更新` | `git pull`，有新提交则展示更新日志；`package.json` 有变化时执行 `pnpm install`；PM2 下自动重启，重启后回原会话报告 |
| `#棋类强制更新` | `git fetch && git reset --hard origin/<当前分支>`，丢弃本地改动后同上 |
| `#棋类版本` | 当前版本号、最后提交时间、最近几条 CHANGELOG |

仅主人可用。正则写作 `/^#?(棋类|chess)(强制)?更新$/i`，不会和柴郡的 `#柴郡更新` 冲突。

### 3.3 走子输入与防误触

- 普通聊天不会被当成走子：只有**本群有进行中的对局**、**发送者是轮到的那一方**、并且**整条消息完全匹配走法格式**时才处理。
- 中文记谱支持：
  - 基本格式：`棋子 + 起始纵线 + 动作(进/退/平) + 目标`，如 `炮二平五`、`马8进7`。
  - 同一纵线有两个同类子：`前车进一`、`后马退二`；三子以上的兵：`前兵`、`中兵`、`后兵`，`一兵` / `二兵`……
  - 红方习惯用中文数字，黑方习惯用阿拉伯数字；**两种数字双方都接受**，渲染和回显时按规范写法输出。
  - 异体字：`帅/将`、`仕/士`、`相/象`、`兵/卒`、`车/俥/車`、`马/傌/馬`、`炮/砲/包` 都能识别。
- 坐标格式：ICCS 坐标 `h2e2`（列 a–i，行 0–9，红方在下）。棋盘图片四周印有坐标，看图就能写。
- 走法非法时说明原因，例如“该位置没有你的棋子”“马脚被绊”“走后己方被将军”“将帅不能照面”，并列出几个合法走法作为提示。

## 4. 规则实现

### 4.1 棋盘表示

- 10×9 数组，外加 FEN（与 Pikafish、象棋巫师通用的 `rnbakabnr/9/1c5c1/...` 格式），方便存档、复盘和对接外部引擎。
- Zobrist 哈希：用于重复局面判断和 AI 置换表。

### 4.2 走法规则

| 棋子 | 规则要点 |
| --- | --- |
| 帅 / 将 | 九宫内直走一步；**将帅不能在同一纵线上直接照面** |
| 仕 / 士 | 九宫内斜走一步 |
| 相 / 象 | 走田字，**不能过河**，**象眼被塞不能走** |
| 马 | 走日字，**蹩马腿**不能走 |
| 车 | 直线任意格，不能越子 |
| 炮 | 移动同车；吃子必须**隔一个子**（炮架） |
| 兵 / 卒 | 未过河只能前进一步；过河后可前进或左右平移，不能后退 |

合法走法 = 伪合法走法中，走完后己方不被将军且将帅不照面的那些。

### 4.3 胜负判定

| 情况 | 结果 |
| --- | --- |
| 将死 | 被将死方负 |
| 困毙（没被将军但无子可动） | 无子可动方**负**（象棋规则，与国际象棋“逼和”不同） |
| 认输 / 超时 | 该方负 |
| 双方同意求和 | 和棋 |
| 自然限着：双方各走 60 步（共 120 步）无吃子 | 和棋（步数可配置） |
| 同一局面重复 3 次 | 如果其中一方一直在**长将**，长将方负；否则判和 |

完整的亚洲象棋规则中“长捉”的认定很复杂（要区分捉的子是否有根、是否属于兑子等）。第一期只实现**长将判负**，其他循环一律判和，帮助里会写明这一点。以后有需要再补“长捉”。

### 4.4 正确性验证

用 perft（统计固定深度下的所有走法数）对照公认数值做单元测试：

| 深度 | 初始局面走法数 |
| --- | --- |
| 1 | 44 |
| 2 | 1,920 |
| 3 | 79,666 |
| 4 | 3,290,240 |

另外加入若干特殊局面的用例：蹩马腿、塞象眼、炮架、将帅照面、困毙、长将。

## 5. 棋盘渲染

### 5.1 方案

使用 TRSS 自带的 `lib/puppeteer/puppeteer.js` 渲染 HTML 模板截图，与柴郡 `#柴郡帮助` 的做法相同：

- 模板 `resources/xiangqi/board.html`：用 CSS/SVG 画木纹棋盘、楚河汉界、九宫斜线、炮兵位标记，棋子是红黑两色的圆形棋子。
- 标注：
  - 上一步的起点和终点用方框高亮；
  - 被将军时帅 / 将闪红圈，并显示“将军！”；
  - 四周印纵线编号：红方底边 `九…一`，黑方顶边 `1…9`；再加一圈浅色 ICCS 坐标 `a–i / 0–9`。
- 顶部信息栏：红方 / 黑方玩家名、当前回合数、轮到谁、上一步的中文记谱。
- 图片约 720×800，PNG 压缩后大约 100–200 KB，两个适配器都能正常发送。

### 5.2 视角

默认**红方始终在下**，群里所有人看到的图一样，坐标也不会混。配置项 `flipForBlack: true` 可以改成“轮到黑方时翻转棋盘”。人机模式下玩家执黑时自动翻转。

### 5.3 降级

如果 puppeteer 不可用（没装 Chromium），改为发送文字棋盘（等宽字符画）。QQBot 下文字会转成 Markdown 代码块，对齐更好。

## 6. 人机对战（AI）

### 6.1 内置引擎（默认，纯 JS）

| 模块 | 做法 |
| --- | --- |
| 搜索 | 迭代加深 + Alpha-Beta（PVS），按时间限制停止 |
| 走法排序 | 置换表最佳着 → MVV-LVA 吃子排序 → 杀手着法 → 历史启发 |
| 静态搜索 | 叶节点继续搜吃子和将军，避免“水平线效应”送子 |
| 评估 | 子力价值 + 位置分表（PST），兵过河加分、车马炮位置分等；参考象棋巫师公开的评估思路 |
| 置换表 | Zobrist 哈希，固定大小 |
| 开局库 | 内置一个小开局库（中炮、屏风马、飞相、仙人指路等常见开局前几步），让开局不呆板 |
| 线程 | `worker_threads` 单独线程运行，主线程不卡；同一时间最多 N 个搜索，超出的排队 |

### 6.2 难度

| 难度 | 搜索设置 | 预计水平 |
| --- | --- | --- |
| 入门 | 深度 1–2，按一定概率随机走 | 会送子，适合新手 |
| 简单 | 深度 3，带少量随机 | 不送子，但看不深 |
| 普通（默认） | 限时 1.5 秒，迭代加深 | 能胜过大多数业余玩家 |
| 困难 | 限时 4 秒 | 业余高手水平 |

### 6.3 可选外部引擎

配置 `engine.uciPath` 指向 Pikafish 可执行文件后，增加 `大师` 难度，通过 UCI 协议通信。不配置时这个难度不显示，插件本身不依赖它。

### 6.4 人机消息节奏

玩家走一步后，Bot 在**同一条回复里**发出“玩家这一步 + AI 应着 + 新棋盘图”。这样每回合只占一次回复，同时满足 QQBot 被动回复的次数和时效限制（见 7.2）。

## 7. 适配器兼容

### 7.1 识别适配器

```js
const isQQBot = e => e.bot?.adapter?.id === "QQBot" || e.adapter_name === "QQBot"
```

只有 QQBot 才附带按钮。LLOneBot 不发按钮，其他行为两边一致。

### 7.2 QQBot 需要注意的地方

| 问题 | 处理 |
| --- | --- |
| 用户 ID 是 openid（绑定后才是 QQ 号） | 房间内玩家用 `e.user_id` 标识，同一适配器内是一致的；战绩按 `e.user_id` 存。QQBot-Plugin 绑定后 `user_id` 会变成真实 QQ 号，绑定前后的战绩是分开的，帮助里会说明 |
| 拿不到群昵称 | 显示名优先用 `e.sender.card / nickname`，没有就用 `@`（QQBot-Plugin 会把 `segment.at` 转成 Markdown @ 标签） |
| 被动回复：每条消息 5 分钟内最多回复 5 次 | 每回合只回一条消息（图片 + 文字 + 按钮合并发送）；超时提醒等“没有用户消息触发”的情况属于主动消息，可能发不出去，失败时只记日志，不影响判定 |
| 群里 input 按钮不能 `send: true` | 群里只用 `callback` 按钮，或 `send: false` 的 input 按钮（只填入输入框） |
| 合并转发 | 更新日志在 QQBot 下由 QQBot-Plugin 的 `forwardMarkdown` 转成 Markdown，无需特殊处理 |

### 7.3 QQBot 按钮设计

**等待加入时**

```text
[ 加入对局 ]  [ 取消对局 ]
```
`加入对局` 是 callback `#加入象棋`；`取消对局` 用 `permission: 发起人ID`，只有发起人能点。

**对局中（每次发送棋盘时附带）**

```text
[ 走法提示 ]  [ 填写走法 ]
[ 悔棋 ]  [ 求和 ]  [ 认输 ]  [ 棋盘 ]
```

- `悔棋 / 求和 / 认输` 用 `permission: [红方ID, 黑方ID]`，旁观者点不了。
- `填写走法` 是 input 按钮（`send: false`），点击后在输入框填入 `#走 `，玩家补全走法发送即可。

**按钮走子（手机端友好，建议第一期一起做）**

不想打字的玩家可以“点两下”走棋：

1. 点 `走法提示` → Bot 列出当前可以动的棋子：`[车九] [马八] [炮二] [炮八] [兵三] …`；
2. 点某个棋子 → Bot 列出这颗棋子的所有合法走法：`[炮二平五] [炮二进四] …`；
3. 点某个走法 → 直接走子。

按钮的 `permission` 设为当前行棋方，只有他能点。按 QQ 限制，每条消息最多 5 行、每行最多 5 个按钮，超出部分分页（`[下一页]`）。

LLOneBot 下没有按钮，`#走法提示` 改为发送文字列表。

### 7.4 两个 Bot 在同一个群

柴郡插件和 QQBot-Plugin 支持官方 Bot 与 LLOneBot 共存，并可以把群 openid 映射成真实群号。如果两个 Bot 在同一群、群号映射后相同，两个 Bot 会收到同一条走子消息。处理方式：**对局属于开局的那个 Bot（记录 `self_id`）**，其他 Bot 收到这个群的对局指令时直接忽略，避免重复回复。

## 8. 房间与状态管理

### 8.1 房间

- Key：群聊 `group:<group_id>`，私聊 `private:<user_id>`。一个群同时只能有一局。
- 同一个人同时只能在一局里（防止同时在多个群开局）。
- 结构：

```js
{
  id, game: "xiangqi", selfId, scope,           // 所属 Bot 与群
  status: "waiting" | "playing" | "ended",
  players: { red: {id, name} | "AI", black: {...} },
  mode: "pvp" | "ai", aiLevel,
  fen, history: [{ move, iccs, cn, fen, captured }],
  repetition: { [zobrist]: count },
  createdAt, lastMoveAt, drawOffer, undoRequest,
}
```

### 8.2 超时（可配置）

| 项目 | 默认 | 结果 |
| --- | --- | --- |
| 等待对手加入 | 5 分钟 | 自动取消 |
| 单步思考 | 10 分钟 | 剩 2 分钟时提醒，到时判负 |
| 悔棋 / 求和请求 | 2 分钟 | 自动视为拒绝 |

计时用单个全局定时器每 30 秒扫描所有房间，不为每个房间单独建定时器。

### 8.3 持久化

- 房间写入 Redis（TRSS 本来就需要 Redis），key 为 `chess:room:<scope>`，带过期时间。
- 插件启动时恢复进行中的对局，所以 `#棋类更新` 重启后棋局不会丢；恢复时重新计算超时起点。

### 8.4 战绩

- Redis Hash：`chess:stats:xiangqi:<user_id>`，存胜 / 负 / 和、积分、连胜。
- 积分用 Elo（初始 1200，K=32）；人机对局只记录胜负，不计积分，防止刷分。
- 排行按群统计：`chess:rank:xiangqi:<group_id>` 有序集合。
- 每局结束时保存棋谱（ICCS 走法串 + 起始 FEN）最近 N 局，为以后复盘做准备。

## 9. 更新功能（参考柴郡插件）

在柴郡 `CheshireUpdate.js` 的基础上实现，流程如下：

1. 校验 `e.isMaster`；用全局锁防止重复执行。
2. 记录旧 commit → `git pull`（强制更新改为 `git fetch` + `git reset --hard origin/<branch>`）。
3. 已是最新：回复“已是最新版本 + 最后提交时间”。
4. 有更新：`git log old..new --pretty="%h: %s"` 生成更新日志，用合并转发发送。
5. `git diff --name-only old new` 包含 `package.json` 时执行 `pnpm install --filter Chess-Plugin`（失败只提示，不中断）。
6. PM2 守护（`process.env.pm_id` 存在）：写 `data/restart.json` 记录会话 → 3 秒后 `process.exit(0)`；重启后读取文件，回原群 / 私聊报告“重启成功 + 新版本号”。
7. 非 PM2：提示手动重启。

和柴郡相比有两处改进：

- 依赖是否变化用 `git diff --name-only` 判断，比匹配 `git pull` 输出更可靠（输出被截断时也能识别）。
- 补上了 `#棋类强制更新`：柴郡的失败提示里提到了强制更新，但没有实现这条指令。

重启前会先把所有进行中的房间写入 Redis（8.3），重启后恢复对局。

## 13. 确认结果（第一期按此实现）

| 问题 | 结论 |
| --- | --- |
| 指令名 | 总帮助 `#棋帮助`（列出所有棋类），各棋种用自己的帮助（`#象棋帮助`）；维护指令 `#棋更新` / `#棋强制更新` / `#棋版本`。中文指令保留；增加英文名 `Chinese_Chess`：`#Chinese_Chess create / join / ai / board / undo / draw / resign / end / help` |
| 超时 | 每步 **120 秒**，超时前 30 秒提醒一次，超时判负（均可配置） |
| 棋盘视角 | ~~红方始终在下~~ → v1.1.0 改为跟随行棋方：轮到哪一方，哪一方在下（`boardFollowTurn`） |
| 红方怎么定 | `#发起象棋` 不指定颜色时，**对手加入、开局时随机分配**；发起人也可以 `#发起象棋 红` / `#发起象棋 黑` 指定。人机对战默认玩家执红先走，可 `#人机象棋 黑` |
| 循环判定 | 长将判负，其他三次重复判和 |
| 战绩 / 排行 | 第一期不做（第 8.4 节延后） |
| 按钮 | 只做发起 / 加入 / 人机 / 取消、对局中的悔棋 / 求和 / 认输 / 棋盘、同意 / 拒绝请求；**不做按钮走子**（7.3 中“按钮走子”取消） |
| Pikafish | 不预留（见下） |
| 仓库 | `Chess-Plugin`，插件目录名 `Chess-Plugin` |

**关于 Pikafish**：程序本身只有几 MB，但还要另外下载神经网络文件（几十 MB），并且要按服务器 CPU 选对应版本；思考时会占满所配置的 CPU 线程，还需要几十到几百 MB 的置换表内存。不满足“不需要额外安装、占用不大”的条件，所以第一期不预留。内置引擎使用与 Pikafish 相同的 FEN / ICCS 格式，以后需要时可以直接接入。

**与设计稿的其他差异**

- 计时改为每个房间单独计时器（120 秒的限时用 30 秒扫描太粗）。
- 战绩相关的 Elo、排行、棋谱存档推迟到后续版本。
- 超时提醒和超时判负的消息优先作为对最后一条走子消息的回复发送：120 秒小于官方机器人 5 分钟的被动回复时限，所以官方机器人下也能发出。
